### Diagnostic patch versus OFF residency

The E0005 OFF arm used the diagnostic source snapshot with Q0 round capture disabled and the identity-only sink enabled. The `MtpDecodeEgress` field reserves `2 × 8 × 10 × sizeof(float) = 640` bytes in the persistent device round buffer and another 640 bytes in its pinned-host mirror. The field is present in both OFF and ON builds because it is part of the egress struct; the tensor aliases that field rather than allocating another device buffer (`round_buffers.h:72-86`, `round_buffers.cpp:146-149,309-312`). This is the only explicit Q0 metric device-storage delta found, and it is present in the OFF baseline already.

ON-only `MtpQ0ObserverTraceBuffer::enable()` reserves 4,096 round records in a host `std::vector` (`program/speculative/q0_observer.h:89-121`). The E0005 prompt/committed identities and sidecar writer also hold and hash CPU-side data. They do not allocate device memory. `ProgramImpl` enables the trace only for `NINFER_Q0_OBSERVER=1` (`program_impl.cpp:79-84`). The graph profile planner is unchanged by that flag; graph capture receives the flag for the metric output path but does not create a simultaneous second graph pool (`graphs.cpp:341-358`). A possible driver-side difference between ON and OFF graph executables was not measured.

## Best candidate for a later bounded gate

The concrete candidate is to set the optional extra `device_state_slots` from 1 to 0 while retaining C=1, `max_context=kv_capacity=188,416`, K7, K8V4, MTP, CUDA Graphs, `max_private_continuations=2`, `max_shared_prefixes=4`, eight host state slots, and 8 GiB host KV. Source defines `device_state_slots` as extra StateImage capacity beyond active lanes; the current two device slots are `C + device_state_slots`. The option accepts zero, so the candidate leaves one active Device slot and all eight Host slots available. When an active image and checkpoint occupy the only Device slot, capture planning explicitly selects `HostSnapshot` if a HostStatePool exists (`program/transactions/capture.cpp:178-192`); it preserves the checkpoint on Host and transfers the unchanged Device replica to the active identity. This keeps the logical checkpoint while changing its physical placement.

The exact device saving expression is the planned `StateImageDevicePool` byte difference for `slot_count=2` versus `slot_count=1`. Its per-slot tensor payload is:

```text
Σ over linear-attention layers L:
    2 × conv_channels × conv_width                 (BF16 convolution state)
  + 4 × key_head_dim × value_head_dim × value_heads (FP32 recurrent state)
+ 2 × hidden_width                                   (BF16 continuation hidden)
+ 256-byte region-alignment differences
```

The fixed FNN startup log says the eight-image host StateImage pool is 1.15 GiB. The formatter rounds this field to two decimal places, so the host mirror implies approximately 146.56–147.84 MiB per image (153,679,299–155,021,476 bytes). The device slot uses the same logical tensors; per-layer alignment can shift the exact pool delta slightly. The device geometry (`linear_attention_layers`, GDN dimensions, and exact `StateImageDeviceLayout` byte count) is absent from the permitted public-safe records, so this is a falsifiable estimate, not an exact measured reclaim. The Program's non-KV residual also bounds one of its two equal StateImage payloads above by 169,459,072 bytes; it does not provide a lower bound.

Against the pre-warmup 28,180,480-byte deficit, the host-derived estimate is about 5.5 times larger and predicts roughly 119.7–121.0 MiB above the 1 GiB gate. The active context, full Main/MTP KV capacity, sampler, and graph policy remain unchanged. Logical cache slots remain configured; the removed resource is one inactive GPU StateImage replica, with host-backed residency and transfers available. The tradeoff is cache restore latency. If the required capability includes one cached GPU-resident StateImage, this candidate does not satisfy that interpretation and should be rejected.

Static source shows request-time KV and scratch use the full-capacity Program arenas allocated at startup; decode Ops do not call the product's `cudaMalloc` path directly. That supports the expectation that removing the slot yields a persistent saving through warmup and requests. The captured graphs depend on StateImage and workspace addresses, so the slot count must be changed before Program planning and graph capture; no allocation can be freed after capture. The E0005 run made no full-context public request, and the exact post-warmup free reading was not retained. Actual worst-case request-time headroom, driver-side graph bytes, and any warmup/lazy-library increment remain unverified.

## Decision and later gate

The optional GPU StateImage slot is the only candidate with a plausible >64 MiB saving that preserves one active lane, full context/KV capacity, logical cache counts, and host fallback. Its estimate is sufficient to justify a later, separately authorized measurement gate. H01 therefore survives the static candidate screen conditionally; it has not passed the required real post-warmup and request-time margin test.
